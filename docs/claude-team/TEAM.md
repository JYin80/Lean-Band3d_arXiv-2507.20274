## 0. 总体架构

| 位置 | 角色 | 做什么 | 不做什么 |
|---|---|---|---|
| **Cowork 主会话**（claude-opus-5-5） | 总调度 | 与 Jun 确认目标和口径；核查并拆解数学目标；写工单规格和钉文；划分文件所有权；处理异常和签字；汇总验收结论；需要时起 Fable 子代理做数学论证；维护路线账本、返工账本、论文–Lean 差异 | 不写 Lean；不在仓库执行任何 git 写操作（查 git 一律 `git --no-optional-locks`） |
| **Cowork 定时任务**（claude-opus-5-5，每小时 :41；RBM2D 的在 :31） | 独立数学监督 | 处理请求队列里的请求；只回答**路线层面**的问题；每天一次兜底检查 | 不派单，不改工单或状态，不放行验收，不合并，不与 Jun 对话 |
| **Claude Code 常驻会话**（Mac，Sonnet，`/loop 10m`） | 执行中枢 | 读 CONTROL；为每张放行的工单开一条带门控的 Workflow；审核通过即自动合并、构建、提交、推送；维护状态文件 | 不做数学或路线判断；不改工单；票面没写清的就标 `blocked` 等总调度 |
| **Claude Code 子代理**（Mac） | 执行团队 | 预审代理只写预审 → 证明代理写 Lean → 全新审核代理独立验收 | 只写本单指定的文件 |

**为什么需要执行中枢。** Cowork 在云端，能读写 Mac 上连接的文件夹，但不能启动 Mac 上的 Claude Code 子代理。它的设备 shell 是一台 Linux 虚拟机，单条命令最长 3 分钟，编不了 Lean。执行中枢就是 Cowork 在 Mac 上的手。它本身不保存状态，所有状态都在仓库文件里，所以会话被压缩或重启都不丢东西。

**通信只走仓库里的文件信箱**（§5）：
- 总调度写工单和 `docs/queue/CONTROL.md`；
- 执行中枢每 10 分钟读一次，把状态和报告写回；
- 总调度每 ≤ 15 分钟心跳一次来读；
- 监督只通过 `docs/supervisor/requests/` 收请求，通过 `docs/supervisor/*.md` 交结论。

### 首轮证明用哪一级模型

> **2026-09-29 起（DECISIONS §63、§65，Jun 的决定）**：下面四类与「多用 Opus」档不再用 `prover-opus`，改用 Sonnet 5.5：较难的用 `prover-hard`（effort xhigh），最难的（下列四类）用 `prover-max`（`prover-hard` 代理，第 1b 阶段 effort 覆盖为 max）；预审一律 `preflight`（Sonnet）。**2026-09-29 21:39 PDT 起（DECISIONS §94）**：Sonnet max 不行（第 1b 阶段证不完、第二次 RETURN，或卡住）就改用 `prover-opus`，第 1b 阶段 effort 覆盖为 xhigh（Opus 5.5），不再先问 Jun，事后汇报；前两种由主控自动升级（CLAUDE.md §3 (B)），卡住由总调度判定。返工率照记，不再据此换档。下文保留作历史。

**主要看工单难度**，返工率只作辅助。下面这些工单的首轮直接用 `prover-opus`：
1. **接口单**：产出会被两张或更多下游工单当作接口，例如新的定义、打包定理、装配定理、gate 的闭合定理；
2. **新路线**：要自己找证明路线，或者要把论文论证改写成另一种形式；
3. **要控制指数**：要自己选择或核对指数、阈值和参数的先后次序，或者某个误差项走到最终归一化时没有富余；
4. **关键路径上的终点单和装配单**（RBM1D 09-28 的教训：关键路径上返工一轮的代价，远大于用 Opus 多花的额度）。

其余用 Sonnet：陈述已由总调度写死、路线逐步给出、指数有富余的票用 `prover`；较长或较难但边界清楚的用 `prover-hard`。**先拆小，让 Sonnet 多做**（§3）。

**返工率**：按合并时间取最近 10 张已结束的工单，数有返工的张数。
- **算返工**：审核退回后修复；开工后发 amend 改目标；开工后作废；合并后被发现接口不合用、要另开票修补。
- **不算返工**：因为 Jun 的新决定而改的；开工前的拆分或 amend；API 故障重跑。
- 返工率 > 30% 时，两可的票改用 `prover-opus`；≤ 30% 为常规档。
- 账本在 `docs/rework-ledger.md`，每合并一张补一行。
- 已开工的票不中途换模型，除非 Jun 豁免。

## 2. 每个证明的流程：带门控的 Workflow（一票一条）

| 阶段 | 谁 | 做什么 | 放行条件 |
|---|---|---|---|
| **0 放行前编译** | 总调度写 `docs/tickets/checks/T####-check.lean`，列在 CONTROL「Pre-release checks」；主控代为编译并回贴输出（总调度的机器上没有 Lean）；总调度看结果、修正后才放行 | 钉文原文、票面点名的上游声明的 `#check`、下游钉文的 `#check`；不含证明、不含 `sorry`（DECISIONS §68、§69） | 编译退出码 0，总调度移入 Released |
| **1a 预审** | `preflight`（Sonnet） | **只做数学**：(i) 指数表（每个指数、阈值、常数的取值、约束与富余）；(ii) 一个具体的非退化实例（数值，脚本核对）。不贴第 0 步、不查名字、不估体量、不写流程。≤ 120 行。**任何地方都不许写 Lean** | 返回「(a) 已写」且 PASS。API 故障可重跑一次，否则记 `preflight-fail` |
| **1b 证明** | 工单指定的角色（`prover` / `prover-hard` / `prover-max`） | 读 (a)，不改它；需要更正就另写 `(a′)`。只在唯一可写文件里写 Lean，模块构建，打印公理，在本单分支提交；**每个终点定理配一个编译过的非空实例** | 构建成功 |
| **2 审核** | 全新的 `auditor` | **以陈述为中心**：比对陈述（脚本 diff）；查空真、隐藏假设和循环；核对每个终点定理的非空实例编译通过；模块构建和公理；paper-delta 覆盖。不查流程；不影响陈述、实例、构建、公理、paper-delta 的报告瑕疵只记观察，不退回。≤ 150 行 | 逐条 PASS / RETURN / BLOCKED |

- **审核 PASS 就自动合并**（CLAUDE.md §3 (A)）：只并本单文件，加根导入，跑全库构建（含 `#assert_rbm_axioms`），提交，推送 main。
- **RETURN 自动修复一次**（§3 (B)）：由 `repairer` 修，修完另起新的 `auditor` 重审。第二次 RETURN、判 BLOCKED、或审核要求总调度签字，都停下来等总调度。
- **报告以脚本输出为主，限定篇幅**（CLAUDE.md §6：prove 报告 ≤ 300 行、其中叙述 ≤ 40 行；审核报告 ≤ 150 行）。
- **报告里的时间、先后和事实，必须来自 `date -u`、工具日志或文件**，说错本身就判不通过。RBM1D 的 Sonnet 证明人在报告里编造过构建时间和 grep 结果，还谎称过先后顺序。
- **总调度签字的常用做法**：
  - 只有报告问题、Lean 已过检查 2–5、票又在关键路径上时，先合并 Lean，下游立即开工；报告勘误另派 `repairer` 并行做，修完做一次只针对勘误项的窄审核（RBM1D 的 H94、H98）；
  - 不在关键路径上的票，照常先修报告再合并（H89、H92）。

### 数学预审持续受阻时
1. 定位真正卡住的数学命题：写出它的精确陈述、已知输入、试过的路线、失败的原因。
2. 总调度起 1–3 个 Fable 子代理，交同一份精确问题。它们只读仓库，交回完整、可核查的论证；命题不成立时交回反例或精确缺口。
3. 总调度复核后，把成立的论证拆成可以独立验收的工单。仍有的缺口保持为阻塞，或者写监督请求。

## 3. 派单

### 拆单
- 只拆已经有完整纸面论证的部分。某个 gate 还没有纸面证明时，先由总调度或 Fable 写出来，或者先派一张只出报告的**设计单**。
- 能由总调度把 Lean 陈述写死（签名、量词次序、常数依赖都定好）、路线逐步给出、指数有富余的部分，切给 Sonnet。这种小单即使被几张下游共用，也不算接口单，因为接口已经由总调度钉死。
- 设计接口、自己找路线、控制指数的核心单留给 `prover-opus`，排在小单合并之后。
- 不为凑单拆；不制造空真或平凡的陈述。
- **相邻的小引理合并成中等大小的票**（约 600–1500 行；Jun，DECISIONS §68）。设计表里相邻、同一文件或同一依赖层、各自不足约 500 行的行，写票时合成一张。
- **写票时总调度先编译核对钉文和上下游接口，再放行**（Jun，DECISIONS §68、§69）：总调度写 `docs/tickets/checks/T####-check.lean`（钉文原文 + 上下游接口的 `#check`，不含证明），列在 CONTROL「Pre-release checks」由主控代为编译；总调度看到编译通过后才把票移入 Released（CLAUDE.md §4 第 0 步）。

### 设计单和摸底单（只出报告，照样审核）
大块工作开工前，先派一张只出报告的 `prover-opus` 设计单或摸底单。报告要包含：
- 目标声明的**钉文**，在临时探针文件里编译过；尚未合并的输入用同类型的本地假设代替，不能用 `axiom`；
- 拆单表，写明每张单的文件和依赖；
- 指数表，表里每一行用到的量都要出现在签名里；
- 具体实例（教训 14）。

审核通过后，总调度照钉文写证明单。RBM1D 的 T1592、T1640、T1656、T1667 都是这样做的，钉文一次写准，后面的票大多一次 PASS。

**尽早派一张覆盖摸底单**（RBM1D 的 T1676）：把论文的主要结论逐条对到将来的 Lean 终点，找出没有任何票覆盖的缺口。RBM1D 在收尾前这样查出了一个没钉住的终点，照字面做会漏掉一条结论。

### 工单规格（`docs/tickets/T####.md`；模板见 `docs/tickets/README.md`）
必须写清：
- 目标声明及数学来源（公式或 label 编号、页码），能钉就钉死；
- 预审的指数表要列的行和具体实例的要求（预审只做数学，DECISIONS §68）；
- 放行前编译核对文件 `docs/tickets/checks/T####-check.lean`；
- 可用的引理，以及已合并的依赖；
- **开工条件**，按调用关系写（教训 11、13）；
- 唯一可写文件；根导入由执行中枢在合并时加；
- 必须通过的构建和公理检查；
- 逐条验收标准；
- 选哪个角色、为什么，以及当时的返工率；
- 必读材料，只列相关章节，不列整份历史文件。

写规格前，总调度亲自逐条核对：所引声明的签名、各假设的量词和作用域、每个加性误差项走到最终归一化后的大小、各前提能否同时满足。核对不了的，写成第 0 步。

**工单写后不改。** 更正另开 `T####-amend-N.md`：
- 开工前的 amend 不算返工，开工后的算；
- 已开工的票要改目标，先停下来，再发 amend。

**不得为了方便拆分，加上比论文和最终目标实际需要更强的要求。** 确实要改论文的假设或结论时，交 Jun 决定（§4）。

### 并行度
- 并行单位是工作组（一条 Workflow）。上限写在 CONTROL（默认 4，最多 5），由 Mac 上能同时跑几个 `lake build` 决定。
- 初始 `parallel: 4`（RBM2D 后期 Jun 的要求：至少同时 4 张在跑）；与 RBM2D 的中枢同时跑时注意 Mac 的 CPU，由 Jun 定。
- 关键路径优先；关键路径的票被卡住时，按调用关系把尾部拆开，让不依赖它的部分先做（RBM1D 的 H96）。
- 待审核的积压超过 10 张时，CONTROL 写 `AUDIT_FIRST`。
- 没有真实目标时不造填充单，记下实际的限制。

## 4. 口径与路线级决定：交 Jun，一次只问一件

- **论文忠实度**（启动时和 Jun 确认，写进 DECISIONS）：
  - 以论文 PDF 为唯一来源。允许明显笔误、必要条件、等价表述这类微小改动，逐条记入 `docs/paper-deltas.md`；
  - 实质性改动由 Jun 决定；
  - 被引文献里的结果要么当作授权的外部输入（逐条列入 DECISIONS），要么内部证明。
- **路线级决定**先报 Jun，附工作量估计。例如换路线、用随机路径还是单时刻分布、新开 gate。
- **Jun 没决定的问题，相关的票一律不开工**。包括「只是确定性部件」的部分，也包括为决定做准备的摸底单，除非 Jun 同意提前摸底。
- **提问方式**：
  - 一次只问一件；
  - 用纯数学说清楚，不用内部符号；
  - 重大数学问题可以先请监督复核（写请求文件），再转给 Jun；
  - 总调度自己解决不了的数学问题，可以先起 Fable 子代理咨询。
- **给 Jun 的汇报**：
  - 用中文，数学术语用英文；
  - 时间一律写洛杉矶时间，仓库文件里照旧用 UTC；
  - 简短，先说结论，再说要他定的事。
- Jun 的决定写进 `docs/DECISIONS.md` 的新一节：先原话，后落实。

**git 纪律**
- 只有执行中枢和它的子代理在 Mac 上做 git 写操作。
- Cowork 一侧（总调度、监督、Fable）永远不做 git 写操作，查 git 用 `git --no-optional-locks`，以免留下锁文件。
- 每张票用自己的分支和工作树，提交只含本单的文件。
- main 上每次合并提交后，执行中枢紧接着 `git push origin main`：只推 main，禁止 force；被拒就停下报告。
- 从不 `git add -A` / `git add .`。

**工作树构建**
- `.lake/packages` 用符号链接共享；`.lake/build` 用 `cp -c -R`（APFS 写时复制）克隆。
- 不用硬链接：Lake 会原地改写 .olean，硬链接会把改动带回主缓存。

**CONTROL.md 保持在 20KB 以内**
- 已完成的指令连同它的 `done:` 行，原样移进 `docs/queue/CONTROL-archive.md`（只追加）。
- 只保留当前在做的票、仍然生效的指令和常设规则。
- 新写的 H 指令要短。
- 编辑时用 Python 先读后写，并比对修改时间，免得覆盖中枢刚追加的 `done:` 行。

## 6. 独立数学监督

- **只管路线层面**：
  - 已派和在做的票串起来，能否到达目标 gate；
  - 是否在反复产出推广不了的特例；
  - 每条路线花了多少单，是否合理；
  - 跨工单的接口和假设（量词、指数、尺度、非退化性）能否同时满足。
  - 逐单的数学核对由预审和审核负责，监督不重复。
- **请求队列**：
  - 总调度需要监督时，写 `docs/supervisor/requests/REQ-<UTC 时间>.md`，首行 `status: open`；
  - 监督每小时 :41 处理所有 open 请求，写出结论 `docs/supervisor/<UTC 时间>.md`，再把请求首行改成 `status: done → <结论文件名>`；
  - 总调度不直接触发定时任务：直接触发要人工点确认，RBM1D 曾因此卡了约 7 小时。
- **写请求的时机**：
  - 每个 gate 的宽口径票数（含返工，但只改报告、Lean 未动的返工不计入）到 25、40（或 45）时各写一次；
  - 路线判定；
  - 同一类缺陷被退回两次；
  - 某个假设可能不可满足；
  - 数学上的重大问题（新路线的钉文、设计单的缺陷、覆盖面风险、总调度签字可能改变数学内容）。
- **到 50 张仍未闭合**，监督自动建议 HOLD，须先做数学评审。
- **结论只有三种**：PASS、建议 HOLD、建议 STOP。HOLD/STOP 须附可核查的来源、精确的数学缺口、最早可见时间，以及此后派出的票。
- 收到 HOLD/STOP，总调度先照办（CONTROL 改 `HOLD`），再向 Jun 报告。
- 等监督结论期间不必停止派单，除非问题本身会让在跑的票白做。

## 8. 教训（来自 RBM1D；每条都付过返工的代价）

1. **路线预算**：同一路线累计约 50 张仍没有闭合 gate，暂停并做数学评审。
2. **先有纸面证明，再拆单。**
3. **写规格前逐条核对接口**：签名、量词、每个加性项走到最终归一化后的大小、各假设能否同时满足。
4. **按定义就满足的见证，也要估一下它的典型大小。** 逻辑上成立的见证，数值上可能大到让下游的前提永远不成立。
5. **docstring 和蓝图不是证据**：「已证」以签名里的假设为准。条件定理不算论文结论。
6. **Cowork 一侧永远不做 git 写操作。** 会话重连后尤其要注意。
7. **监督只管路线，按请求运行**；让它每次通读全部材料，开销可达项目总量的两到四成。
8. **难的票首轮就用高级模型。** 主要看难度：接口、新路线、控制指数、关键路径终点。
9. **票面没钉的辅助引理一律 `private`，或以文件名作前缀。** 并行的票在同一命名空间里加公开名，会撞上钉住的名字。
10. **设计单钉的签名，要带上指数表用到的每一个参数。** 审核要逐行核对：表里每一行用到的量，签名里都有。
11. **写开工条件时，逐一列出本票要用到的、由别的票新给出的引理**，不能只看导入层次。
12. **Jun 没决定的问题，相关的票一律不开工**，包括「只是确定性部件」的部分和为决定做准备的摸底单。
13. **并行的兄弟票，开工前按调用关系逐对扫一遍。** 要检查 B 的原文件是否用到 A 的原文件里的公开名字。扫描时名字前面可能带命名空间前缀，例如 `Grid.foo`，匹配短名时不能把前面的「.」当成边界排除。
14. **外部假设要做一次具体的极限核算，不能只核对文字。** RBM1D 照抄 [51, (2.9)] 的原文，原文漏了一个归一化因子，结果写出的假设与其他前提矛盾，已合并的定理成了空真。以后凡是引入外部假设，预审和审核都要在具体情形下（例如 k = 1、体内能量）算出两边的极限，确认一致。
15. **顺序靠拆阶段来保证，不能只写在提示词里。** 「先写预审再写 Lean」只写在提示词里时，Sonnet 证明人先起草了 Lean，事后补写预审，还编了时间。现在第一阶段拆成预审代理和证明代理两步，中枢按返回结果放行（CLAUDE.md §4）。
16. **报告里的事实要可核查。** 报告中每个时间、先后、「跑过某命令」「某名字没有外部调用」的说法，都必须能在工具日志或文件里找到；说错本身就判不通过。关键路径上连续出这类问题，剩下的票改用 Opus。
17. **中枢的 Workflow 要按阶段结果放行。** 预审阶段因为 API 过载没写出东西，中枢仍启动了证明阶段。每个阶段都要返回结构化结果，下一阶段只在结果满足时启动。
18. **尽早做覆盖摸底**（§3），找出没有任何票覆盖的终点。
19. **关键路径被卡住时，按调用关系拆尾部**，让不依赖它的部分先做；拆单在开工前做，不计返工。
20. **CONTROL 写时间用 `date -u`**，不要按预估写一个将来的时间。
21. **报告里凡是「检查过」「跑过」「grep 显示」，都要贴出命令和原始输出，不写编辑和构建的经过**（RBM1D 监督 0839，2026-09-28）：GU 链有五轮只改报告的返工，全是编出来的经过或没跑过的检查；用 Opus 写的票也出过一次。审核对承重结论（覆盖范围、见证、闭包扫描、签名比对）一律从原始来源重建，重建不了才退回 Lean；其余不实的叙述只算报告缺陷。
22. **旧模式留下的计划和说法按未核实处理**（Jun 2026-09-28 21:23 UTC：「你接手时 这个文件夹里的一些旧计划有一定概率是错的， 所以要注意」）。PLAN、STATUS、random-layer、archive、paper-deltas 旧条目（#1–#27）、蓝图、Lean docstring 里的说法，只作线索；写进工单或报告之前，要对照论文原文和 Lean 签名重新核实并贴证据（CLAUDE.md §5.10）。已发现的一例：Step 2 用一时刻律加连续归纳的旧计划（监督 2055 否定）。总调度写票时同样遵守：票面引用的旧说法要么自己核过，要么写成第 0 步核对项。
23. **随机层的命题从一开始就按随 `N` 变化的能量 `E : ℕ → ℝ` 写**（RBM1D DECISIONS §8h 的教训；RBM2D DECISIONS §15）：RBM1D 先在固定 `E` 下做完 Steps 1–5，再为终点的能量一致性补做 GU 线——重述 250 条定理、28 张票。写沿尺寸序列的钉文（`≺`、步条件、Step 输入输出）时，能量取序列；矩阵层泛函与确定性尺度仍对单个 `E` 定义。
24. **票面引用源文件时按声明名，行号只作辅助且须核过**（RBM2D 2026-09-29：T2044 的报告退回有一部分源于票面给的探针行号差了几行，预审照抄后被审核判为不实）。总调度写票时给出声明名；行号要给就用 `grep -n` 当场取。仅报告的退回也算返工，但与模型档位无关（Opus 也出），对策是流程（CONTROL H15、H18），不是升级模型。
25. **要由别处证明的「假设形状」钉文，设计审核必须试它能否为真**（RBM2D 2026-09-29：T2006 给 P7c 钉的 `SumDecayDetHyp`、`SumDecayCase5Hyp` 照字面为假——`A ≡ 1` 一试就破——使 P7b 的三个目标空真；T2006 的审核和监督的钉文核对都只查了见证与空真，没试极端输入）。审核对每条这类钉文至少用一个极端输入（常数张量、`W = 1`、`t → 1`、`L` 大）检验；论文里的 `C_n W^{C_nτ}` 一类常数是渐近的，钉成确定性界前要确认带上 `N ≥ N₀` 与论文默认的条件。
26. **签一条改钉文形状的 paper-delta 时，当场 grep 所有探针与票面里同一陈述的其他副本**（RBM2D 2026-09-29：T2049b 在 §18 签字，指出 (`GijGEX`) 在对角上不成立；T2006 探针里的 `GbEXPHyp` 是同一陈述的另一副本，照样留在 T2051 的抄录清单里，直到 T2051 预审才被拦下，T2051 因此返工）。签字当轮就对 `git show <探针提交>:<文件>` 与 `docs/tickets/` 搜同名标签（如 `GijGEX`），凡是副本一律标出并由票面修正或移除。
27. **把路线问题交监督时，列出所有钉文里带受影响量的已放行行**（RBM2D 2026-09-29：REQ-0608 只把 E.4 及其直接后继列为受阻，漏了钉文里带同样指数的 E.6b（T2058）、E.8（T2059），监督 0654 替我补上）。写 REQ 前对设计探针按钉文名 grep 受影响的量（指数、控制项），凡已放行而未开工的一律先暂停（HOLD），答复后再按需补丁。
28. **票面给的示例（检验族、见证、实例）写票前对照类或钉文的定义核一遍**（RBM2D 2026-09-29：T2076-amend-1 以 `A ↦ Re tr A` 作 `HermTestFun` 的检验例，但它无界、不满足 (H2)，证明者编译了反例并改用 `sin ∘ Re tr`；DECISIONS §28）。
29. **H 指令一写进 CONTROL 就算已发出，不再改它的文本或文件表；要补就发新 H**（RBM2D 2026-09-29：总调度在 H48 还没有 done 行时往里加了 T2094，主控已按原文执行，T2094.md 漏提交；DECISIONS §29。「没有 done 行」不等于「还没读」）。

## 9. RBM2D 后期定下的常规（2026-09-29 至 10-02；RBM2D DECISIONS 节号附后，供查原文）

1. **首轮模型**（§63、§65、§94）：难票首轮用 Sonnet 5.5：较难、边界清楚的用 `prover-hard`（xhigh）；最难的（接口单、自找路线、控制指数、关键路径终点或装配单）用 `prover-max`（`prover-hard` 代理，第 1b 阶段 effort 覆盖为 max）。Sonnet max 不行（1b 没证完、第二次 RETURN、或 60 分钟无进展）就在同一分支重跑 1b，用 `prover-opus`，effort 覆盖为 xhigh；前两种由中枢自动升级，卡住由总调度判定。预审一律 `preflight`（Sonnet）。
2. **流程简化**（§68–§70）：预审只做数学（指数表 + 一个具体实例）；审核以陈述为中心；每个终点定理配编译过的非空实例（其他 gate 尚未证出的钉文前提可留作 `example` 的假设）；报告以脚本输出为主、限定篇幅；相邻小引理合成中等大小的票（约 600–1500 行）；写票时先由中枢编译检查文件，通过才放行。
3. **数学卡住就上 Fable 5.1 子代理**（§229、§231）：预审因数学 BLOCKED/FAIL、审核因数学 RETURN 且修复后仍不过、证明人报数学缺口、总调度自己定不下陈述或路线——都算卡住。默认起 1 个；只有要另找接口或路线时才起 2–3 个。子代理只读、不写 Lean、不做 git 写操作；总调度复核后写 amend 或拆票。
4. **流程上的事总调度自己定，不问 Jun**（§166 等）：放行、拆票、amend、心跳、归档、模型升级都自动进行，事后汇报。只有路线级、口径级、资源级的事问 Jun，一次一件。
5. **并行**（§162、§235）：保持至少 4 张在跑或可放行；但「不为凑单拆；不制造空真或平凡的陈述」高于这个数字。
6. **接口规则**（§224）：一个范围里被后续票用到的声明一律公开，加统一前缀（如 `Duhamel_`、`Hyp_`），陈述在 stage 1a 由脚本列出，下游票照这个接口写；其余辅助引理 `private` 或以文件名为前缀。
7. **检查文件的名字核对**（§236）：带依赖的检查文件，等依赖合并后，总调度先逐名 grep 核对（预审报告里列的公开名在 1b 可能被合并的等价物取代），再交中枢编译。
8. **尺度统一**（§214、§216）：随机控制与确定性控制在同一条链上用同一个尺度参数（RBM2D 用矩阵尺寸 `d.size`），开链前定死并写进第一张票；中途换尺度要回头补一整条链。
9. **能量与参数沿序列**（教训 23、§15）：沿尺寸序列的钉文，能量从一开始取 `E : ℕ → ℝ`。
10. **心跳**（§166）：心跳消息固定，不用 `update_trigger` 改（改了要 Jun 在电脑上批准）；进度状态写在 `docs/claude-team/HEARTBEAT-STATE.md`（不进版本库），每轮读、每轮更新。
11. **简单任务总调度自己改**（§243）：论文措辞与引用一类已裁定的局部勘误、Lean 里只动注释或文档串的修改、记录文件，由总调度直接改，不开票、不走中枢工作流；需要入库的随下一条例行提交 H 一起交。Lean 的陈述与证明照旧走票。
12. **外部输入要对照最新版本**（§241）：被引文献的结果作为授权外部输入时，核对作者的最新版本（arXiv 版本号），把版本写进钉文的文档串；发现原文笔误时先查新版本是否已改。
13. **收尾与发布**（§244、§245）：全部终点证完后，用常量闭包工具 `docs/claude-team/tools/DeadDecls.lean` 列出从终点不可达的声明，一张票删完（跨目录互相引用，按目录分开删的话构建不过），注释里的票号与流程字眼另开票清理；GitHub 上只留论文与证明，旧历史本地备份后覆盖一次 `main`（Jun 的决定，RBM2D §244）。
14. **CONTROL 每超过约 20KB 就归档**（§231）：已完成的 H 块、已放行的 Pre-release 行、merge log 除最后 6 行外，原样移进 `CONTROL-archive.md`；脚本范例 `docs/claude-team/tools/example_bookkeeping_archive.py`。
